## Blockers

### BLOCKER-01 — B2B wholesale tier is transactable by any unauthenticated caller

The wholesale price gate is applied consistently on every read surface and on no write surface.
`api/src/routes/orders.ts:219` accepts `body.tier` verbatim and resolves prices from it at `:259`
and `:329`. A guest on the public web store — who cannot *see* wholesale prices — can still buy at
them by sending `{"tier":"b2b"}`.

This is a live authorization defect on a money path, reachable without credentials.

**Affects:** INV-02, CUST-02.

**This is not a regression of D-08 / T-03-21.** Those decisions are scoped to price *visibility* —
`03-08-PLAN.md:122` classifies T-03-21 as "Info disclosure | B2B price ก่อนอนุมัติ", 03-06 gated
`/me/b2b/prices`, and 03-13 closed the catalog read surface. The order **write** path was never
inside that scope. This is a distinct hole that was never closed, not a reopened one.

**Fix:** one guard near `orders.ts:219` — `wholesaleVisible()` already exists at `b2b.ts:87`.

**RESOLVED (quick task 260718-vue, 2026-07-18):** the write-path gate is closed. `orders.ts:224-252`
now calls the SAME `wholesaleVisible()` rule before both price-resolution loops — guest and
non-approved members get `403 not_b2b_approved` and no order row; it fails closed on a DB error
(unlike the catalog's deliberate fail-open, IN-03). Pinned by
`api/tests/order-b2b-tier-gate.test.ts` (5 cases, mutation-verified: deleting the guard fails all
three rejection cases). Full API suite 388 pass / 0 fail. **Known residual, tracked separately:**
knowing an approved customer's UUID still lets a caller place a wholesale order "as" them — that is
the pre-existing member-linkage trust model already shared with the b2c path (any UUID-knower can
attribute a b2c order to a member), not part of this fix.

### BLOCKER-02 — B2B standing orders reserve stock but never generate orders

`reserveStanding` (`api/src/services/b2b.ts:60-78`) performs the atomic reservation correctly, then
stops. No order is ever inserted. The reserved plants sit ahead of B2C demand at round-open and are
never paid, never packed, never released.

The subscription path does the same reservation and *then* inserts an order at
`subscription.ts:277`. That asymmetry is what makes this a gap rather than a deliberate design.

**Affects:** CUST-02, Flow C.

**Open scope question for the owner:** was *automated* standing-order generation in v1.0 scope, or
was conversion always meant to be a manual invoice step? If manual, the missing generation
downgrades to a documentation gap — **but the stranded reservation is a real defect either way.**
Reserved plants with no release or expiry path eat B2C availability at round-open and never come
back.

**Fix:** generate the order post-commit (mirroring `subscription-generate`), **or** explicitly
release/expire standing reservations. Today neither happens.
