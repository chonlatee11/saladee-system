Deliver the database slice end-to-end: the RBAC-ready schema (`users` + role enum), the dual-connection client (pooled+`prepare:false` for runtime, direct/unpooled for migrations), a generated migration WITH a hand-written down, a tiny down-runner, and `/health/ready` that pings the DB. Output: A migrated PostgreSQL with `users`/role enum, reversible migrations, and a DB-backed readiness probe.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| API process → PostgreSQL | Parameterized queries only; connection strings from env |
| migration tooling → prod DB | drizzle-kit uses the DIRECT url; runtime uses pooled |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-00-04 | Tampering | SQL injection on future query surfaces | mitigate | Drizzle parameterized queries only; never string-concat SQL (schema/client set the pattern now) |
| T-00-05 | Denial of Service | prepared-statement errors under load on Neon pooled | mitigate | postgres.js `prepare:false` on pooled endpoint (Pitfall 2) prevents cascading 500s during NFR-01 spikes |
| T-00-06 | Info Disclosure | DB credentials in source/logs | mitigate | Connection strings only from `env` (validated at boot); readiness probe returns status only, never connection details |
| T-00-07 | Availability | irreversible/failed migration blocks deploy | mitigate | Hand-written down SQL + up→down→up test (Criterion 2); BLOCKING apply step verifies before verification |
</threat_model>
