D-17 requires an opt-out mechanism; the `<specifics>` require a re-consent prompt on the next order after a version bump. Both are customer-facing LIFF surfaces sharing `CheckoutWizard.vue`, so they belong in one plan.
Output: LIFF coupon/points fields, segment auto-apply, opt-out route + surface, version-aware re-consent.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → POST /orders | LIFF client may send couponCode/redeemPoints; must never send a resolved price/discount. |
| member → marketing opt-out | Opt-out mutates the marketing consent trail; must be member-authenticated and append-only. |
| settings version → checkout | A bumped pdpaPolicyVersion must force a fresh consent before an order proceeds (PDPA). |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-32 | Tampering | client-inflated discount/points from LIFF | high | mitigate | Client sends only couponCode + bounded redeemPoints; server resolves the money (Plan 03); mirrors T-04-07 |
| T-04-33 | Repudiation/Privacy (PDPA) | opt-out not honored by broadcast | high | mitigate | Opt-out appends granted=false; broadcast latest-row filter (04-06) excludes them; consent-optout.test.ts asserts exclusion (D-17, NFR-04) |
| T-04-34 | Tampering | mutating an existing consent grant | high | mitigate | optOutMarketing + re-consent are append-only INSERTs; test asserts prior rows unchanged |
| T-04-35 | EoP | guest opting out / reading another member's consent | medium | mitigate | Routes behind the me-orders line_user_id member gate (guest → 403, missing token → 401) |
| T-04-36 | Spoofing | guest earning/redeeming points via LIFF | medium | mitigate | PointsRedeem member-only; guest never sees the redeem control (Pitfall 5) |
